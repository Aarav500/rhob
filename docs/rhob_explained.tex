\begin{abstract}
\noindent
This document explains a project called RHOB. It assumes you know what
reinforcement learning is and nothing else about the project. Every term is
defined the first time it is used. Section~\ref{sec:index} is an index that
maps each question you asked me by email to the section that answers it.

Short version of the whole thing: I built a set of test problems for programs
that try to spot cheating agents. I reported a headline number of $0.994$. Then
I checked my own construction and found the number was an artifact of a coding
convention I had imposed on myself. Under a control that removes the artifact
it falls to $0.508$, which is chance. Most of what remains is the method for
building and checking such test problems, not the scoreboard.
\end{abstract}

\section{What this document is}

You asked me to explain the purpose and the techniques of the project, and to
say clearly why it matters. You also said, correctly, that my earlier
explanations were unclear and that some of my words sounded borrowed. I have
tried to fix both. Where I use a term that I think is jargon, I define it in
one sentence and then use plain words afterwards.

Two habits I am trying to follow here, because you flagged both:

\begin{itemize}
\item Every number comes with what it was measured on and how many samples it
      came from.
\item Where a result was withdrawn or a claim failed, that is stated in the
      main text and not in a footnote. There are several. They are the most
      useful part of the project.
\end{itemize}

\section{The sixty-second version}

An agent is trained to maximise a score. The score is written down in code by a
person. It is almost never exactly the thing the person wanted. So an agent can
get a very high score by finding a flaw in how the score is computed, instead
of by doing the task. People call this \emph{reward hacking}.

Suppose you want to write a program that watches a finished training run and
says ``this agent was gaming the score'' or ``this agent was doing the task''.
How would you know if your program works?

You need examples where you already know the answer. RHOB is a set of such
examples: 33 small task families, each of which produces two runs --- one where
the agent gamed the score, one where it did the task properly --- built so that
the visible score is about the same in both. Then 30 candidate watcher programs
are run on those examples and scored on how often they get it right.

That is the whole shape. The rest of this document is (a) what each of those
words means precisely, and (b) what went wrong when I checked my own
construction.

\section{Vocabulary}
\label{sec:vocab}

You said several of my words could mean many different things. Here is exactly
what each one means in this project. This is the section to come back to.

\begin{description}

\term{Proxy reward}
The number the agent actually optimises. It is a real function, written in
Python, that the environment computes at every step. In this project it is
recorded once per episode.

\term{True reward}
A \emph{second} number, also written in Python by the person who built the task,
that measures what we actually wanted the agent to do. The agent never sees it
and never optimises it. It exists only so that we, the people running the
experiment, know which behaviour was the honest one.

\term{Oracle}
Just a name for the true reward and for anything allowed to read it. It is not a
model, not an LLM, not a human. It is the second scoring function described
above. I should have said ``the true reward'' instead of ``the oracle'' from the
start; the word adds nothing.

\term{Run}
One complete recorded training run of one agent on one task variant. It is not a
policy and it is not a single trajectory. It is a time series over training. In
the tabular task, for instance, it is $500$ episodes, and it is stored as four
arrays of length $500$: the proxy reward per episode, the true reward per
episode, a state-visit histogram per episode, and one behavioural number per
episode. Section~\ref{sec:levels} says what each of those is.

\term{Cheating run / hacking variant}
A run produced by the arm of the task that gets its score by exploiting the flaw.

\term{Honest run / legitimate variant}
A run produced by the arm of the task that gets its score by doing the task.

\term{Pair}
The two arms together, plus the machinery that generates them. One pair is one
matched comparison.

\term{Family}
A generator that can produce such pairs at a requested difficulty. There are 33
of them. ``Family'' rather than ``environment'' because one family produces many
pairs, at five difficulty settings, at many random layouts.

\term{Cell}
One (family, difficulty) combination. $123$ cells exist across the 33 families.
A cell is the unit that gets scored.

\term{Detector}
A candidate watcher program. Section~\ref{sec:detector} defines it precisely.

\term{Entry check}
A test that a candidate pair must pass before it is allowed into the test set at
all. This is the thing I was calling an ``admission criterion''. You were right
that the phrase is opaque; ``entry check'' is what I mean, and
Section~\ref{sec:gate} is the part of the project I actually care about.

\end{description}

\section{What a pair is, and the honest answer about learning algorithms}
\label{sec:pair}

You asked: \emph{are the learning algorithms the same? The reward functions? Can
we view these variants as two seeds optimising the same reward?}

The honest answer is no, and this is the single largest limitation of the
project. It is written down in \code{docs/THREAT\_MODEL.md} and it should have
been the first thing I told you.

\textbf{In 28 of the 33 families, neither arm learns anything.} Both arms are
hand-written policies. I wrote a script that behaves the way an exploiting agent
would behave, and a script that behaves the way an honest agent would behave,
and I ran both. There is no learner and there are no seeds of a learner. The
seeds vary the layout and the environment noise, not an optimisation process.

The remaining 5 families are a partial exception. They run real policy-gradient
ascent against a reward model that was genuinely fitted from preference data. In
those, the \emph{exploitation} is emergent --- nobody scripted the exploit ---
although the vulnerability in the reward model, and the label saying which arm is
which, are still designed.

So what does the benchmark establish, given that? It establishes what is
detectable \emph{in principle} from each information channel. It does not
establish what real learned agents leave behind. Those are different claims and
I conflated them in earlier write-ups.

What is the same across the two arms of a pair: the task, the proxy reward
function, and --- after a calibration step --- the \emph{amount} of proxy reward
earned. What differs: the behaviour, and the true reward.

\subsection{Matching}

The two arms are calibrated so that the proxy reward they earn is statistically
indistinguishable, while the true reward clearly differs. This is the point of
the whole construction, so it is worth stating why.

If the cheating arm simply earned more visible score than the honest arm, then a
detector could just look at the visible score and be right. It would have learned
nothing about cheating. It would have learned that this benchmark gives cheaters
higher numbers.

By forcing the visible score to be equal, any detector that succeeds \emph{must}
have read something other than the visible score. And because the extra
information is handed out in named channels, you know exactly which one it read.

\section{The four access levels}
\label{sec:levels}

You said each of ``reward only'', ``state visitation'', ``behavioural'' and
``oracle'' could mean a variety of things. Precisely, from
\code{src/rhob/v3/access.py}, a detector at a given level is handed a copy of the
run with everything above its level deleted:

\begin{center}
\begin{tabular}{@{}llp{8.1cm}@{}}
\toprule
Level & Field added & What the array actually contains \\
\midrule
L0 & \code{proxy\_rewards} &
  A float array, one entry per episode: the proxy reward that episode. \\
L1 & \code{state\_counts} &
  An integer array, episodes $\times$ bins: how many times each discretised
  state was visited in that episode. \\
L2 & \code{behav\_trace} &
  A float array, one entry per episode: one hand-written summary number
  describing the behaviour that episode. On a gridworld it is (mean row visited)
  minus (mean column visited); in a continuous task it is mean $x$ minus the
  centre. \\
L3 & \code{true\_rewards} &
  A float array, one entry per episode: the true reward. \\
\bottomrule
\end{tabular}
\end{center}

Three things about this table matter more than the table.

\textbf{Enforcement is structural, not a promise.} The function \code{restrict()}
builds a fresh object with the disallowed fields set to \code{None} or empty. A
detector at L0 cannot read \code{behav\_trace} because there is nothing there to
read. It is not a rule that a contributor might forget.

\textbf{L3 is not a real access level.} No practical monitoring system gets the
true reward; if you had it you would not need a detector. L3 exists as a
\emph{ceiling}: it tells you how well detection could possibly do on these tasks.
It should never be quoted as a practical result.

\textbf{L2 is hand-authored, and that is a problem I have only half-fixed.} The
behavioural number was chosen by me, knowing which arm was the cheating one. I
chose an axis that I knew separates them. Section~\ref{sec:bug} is about what
that cost me. Rebuilding the L2 channel out of label-blind summaries of the raw
trajectory is work I have not done.

\section{What a detector is, and what ``fit'' means}
\label{sec:detector}

A detector is a class with two required methods.

\begin{itemize}
\item \code{classify(run)} takes one run, already stripped to the detector's
      access level, and returns a number between $0$ and $1$. Higher means
      ``I think this is the cheating one''. It does not have to be a calibrated
      probability; only the ordering is used.
\item \code{detect\_onset(run)} returns which episode it thinks the cheating
      started, or $-1$. This half of the project is currently unvalidated and I
      am not making claims about it.
\end{itemize}

Most detectors are a fixed statistic. ``Does the reward curve flatten and stay
flat?'' ``Is the reward distribution skewed?'' ``How far apart are the two
state-visit histograms?'' Nothing is trained; the same formula is applied to
every run.

\subsection{What ``fit'' means}

Some detectors additionally expose a method called \code{fit(runs\_a, runs\_b)}.
That method is handed the two groups \emph{with the labels attached} --- these
are the cheating runs, those are the honest ones --- and trains on them.

The benchmark decides how to score a detector with one line: does this object
have a method named \code{fit}? If not, apply it to each run directly. If yes,
run 5-fold cross-validation --- train on four fifths of the runs, score on the
held-out fifth, rotate.

Cross-validation keeps this honest: such a detector is never scored on runs it
was trained on, so the number is not leaked and is a real measurement. But it
answers a different question:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
Unsupervised detector & ``Does this fixed statistic separate the two arms?'' \\
Label-fitted detector & ``Is the difference learnable from labelled examples?'' \\
\bottomrule
\end{tabular}
\end{center}

Averaging both into one number per access level answers neither. It reports
whichever question happened to give the bigger number. Section~\ref{sec:five} is
what happens when you separate them.

\section{What the score means}
\label{sec:auroc}

The score is AUROC. In plain words:

\begin{quote}
Pick one cheating run and one honest run at random. AUROC is the probability
that the detector gave the cheating one the higher number. A tie counts as half.
\end{quote}

So $0.5$ is a coin flip, $1.0$ is always right, and $0.0$ is always exactly
wrong (which would be a perfect detector with its sign backwards).

You asked whether a high score would indicate ``a lot of reward hacking, or a
little''. Neither --- and this is worth being explicit about, because it is a
natural reading of the number and it is wrong. AUROC here measures how well the
detector \emph{separates} two groups. It says nothing about how much hacking
occurs in the wild. In this benchmark the mix is exactly 50/50 cheating and
honest by construction, so the benchmark cannot say anything about base rates at
all.

Scores are computed per cell and then averaged upward: per detector per family,
per access level, and so on.

\subsection{The 0.994 specifically}

$0.994$ was not the ordinary score. It was the \emph{cross-family transfer}
score: fit the detectors on some families, then test them on families they had
never seen. If that number were real, it would mean something genuinely
interesting --- that a detector trained on one kind of exploit catches kinds of
exploit it was never shown. Detection would generalise across mechanisms.

It was not real.

\section{The bug: a style rule that became the answer}
\label{sec:bug}

You asked what I meant by ``a coding convention'', and whether I meant that I set
myself a convention that affected the logic of the code. Yes. That is exactly
what happened, and you are right that it is a serious thing to have done.

\code{CONTRIBUTING.md} --- the contributor guide, a document about house style
--- required that every family's behavioural number be \emph{anti-symmetric}
across the pair with one fixed orientation: positive for the cheating arm,
negative for the honest arm. The reason was tidiness. It made the families
comparable and the plots consistent.

The main L2 detector scored a run by taking the mean of the last 100 entries of
that number. The benchmark computed AUROC with ``cheating'' as the positive
class.

Put those three facts together: \textbf{the sign of the observation was the
label}. The detector was not reading behaviour. It was reading my style guide.
A detector that ``transfers to an unseen hacking mechanism'' had discovered that
all 33 families were written by the same person following the same rule.

\subsection{The tell I ignored for months}

There was a symptom in the data the whole time. Each family has a difficulty
knob that controls how far apart the two arms are made to be. L2 AUROC was pinned
at exactly $1.000$ across \emph{every} difficulty setting in 12 of the 13
families whose knob was swept --- the knob moved the separation and the score did
not budge.

That is impossible for a real measurement, and obvious in hindsight. A knob that
changes how far apart two things are cannot fail to move a statistic that
measures how far apart they are --- unless the statistic is not measuring that.
The sign was already the answer, so distance was irrelevant.

\subsection{The fix}

The fix is in \code{src/rhob/v3/sign\_randomization.py}. For each (family,
layout) pair, a deterministic keyed digest produces $+1$ or $-1$. Both arms'
behavioural numbers are multiplied by that one value before any detector sees
them.

Multiplying \emph{both} arms is what makes this a de-biasing step rather than a
destructive one. It is a flip of the coordinate axis the pair is defined on, not
noise added to individual runs. Flipping the two arms independently would not
hide the direction; it would destroy the pair, because the anti-symmetry
\emph{is} the pair. Every magnitude is preserved exactly, so the entry checks and
the difficulty knob are unaffected. The only thing removed is the global constant
that let a detector read the label off a sign.

Result: the cross-family transfer score falls from $0.994$ to $0.508$. The L2
suite mean falls from $0.7229$ to $0.5629$.

\section{Am I sure about the 0.508?}
\label{sec:sure}

You asked this directly. Here is what I have and what I do not.

\textbf{What supports it.} The comparison is like-for-like: sign randomisation is
a single flag, and turning it off reproduces $0.994$ exactly. The $0.508$ is not
one run --- the suite was replicated over 20 independent draws, each with its own
layout and rollout seeds, giving 600 detector-passes, with 95\% intervals from a
percentile bootstrap over the 20 draws.

\textbf{What ``chance'' means here.} $0.508$ against $0.5$ is not distinguishable
from a coin flip given this sample. It is not a claim that the detectors are
slightly better than chance.

\textbf{What would overturn it.} The randomisation hides the direction from any
\emph{single} run, but a detector is also allowed to look at a whole batch of
runs without labels, and could in principle work out the orientation from the
population. That is legitimate and I have not shown that no detector can do it. A
detector that oriented itself that way and still transferred would put the number
back up, and would deserve to.

\textbf{One leak I know about and have not closed.} At L2 a detector also sees
the state-visit histograms, and those are not flipped --- a histogram over a
family's own grid has no benchmark-wide sign to flip. A family whose histogram
bins encode the same spatial axis as its behavioural number therefore still
carries, in principle, enough information to recover the old orientation. Nothing
in the repository does this today, and doing it deliberately would be reading the
label by a longer route. It closes properly only when the L2 channel is rebuilt
without a hand-authored axis.

\textbf{The honest limit of the fix.} Sign randomisation removes the direction
freebie and only that. The behavioural number is still a feature I chose knowing
the answer. So an L2 score measured under randomisation means ``this detector did
not need the sign convention''. It does not mean ``the L2 channel is blind to the
label''.

\section{Entry checks: the part I think is actually worth something}
\label{sec:gate}

You said ``admission criteria'' sounded weird and had probably leaked into my
vocabulary. Fair. Here is the idea without the phrase.

A matched pair is a \emph{claim}: I assert that these two arms earn the same
visible score while doing different things. An assertion is not a fact. So before
a pair is allowed into the test set, it is tested. Six tests per cell:

\begin{enumerate}
\item The two arms earn the same visible score on average.
\item The two arms' visible scores have the same \emph{shape}, not just the same
      mean --- checked with three different shape-sensitive statistics.
\item The behaviour genuinely does differ between the arms.
\item The true rewards genuinely do differ.
\item The moment the cheating starts can be located consistently.
\item The cheating persists to the end of training rather than fading.
\end{enumerate}

\subsection{The interesting part: what test 1 used to be}

Until the audit, test 1 was literally this:

\begin{center}
\code{abs(mean\_auroc - 0.5) < 0.10}
\end{center}

That is: run a reward-only detector, and if it fails to separate the arms,
conclude that the arms are matched. In other words, ``I failed to find a leak''
reported as ``there is no leak''.

That is only as strong as the experiment's power to find a leak, and this
experiment had almost none. At the then-default four seeds per side per layout,
the standard error is exactly $0.0625$. So:

\begin{center}
\begin{tabular}{@{}lc@{}}
\toprule
If the true value were\dots & \dots the old test passed it this often \\
\midrule
$0.500$ (genuinely matched) & 89.6\% \\
$0.556$                     & 76.2\% \\
$0.611$ (\textbf{leaking})  & \textbf{43.5\%} \\
$0.714$                     & 2.5\% \\
\bottomrule
\end{tabular}
\end{center}

A family that was clearly leaking passed nearly half the time. Worse, the
incentive runs the wrong way: \emph{noisier} data made the test easier to pass,
because a noisy measurement is more likely to land near $0.5$.

\subsection{The fix, and what it cost}

Replace the difference test with an \emph{equivalence} test (two one-sided tests,
TOST). The plain-language difference:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
Difference test asks & ``Can I show these differ?'' \\
Equivalence test asks & ``Can I show these are close?'' \\
\bottomrule
\end{tabular}
\end{center}

Now the burden of proof is inverted. To pass, the whole confidence interval must
fit inside $0.5 \pm 0.10$. Noise makes a wide interval, and a wide interval
cannot fit. Noise now makes passing \emph{harder}, which is the correct
direction.

The margin stayed at $0.10$, so the scientific claim did not change. What changed
is the sample size needed to support it, and the change is large:

\begin{center}
\begin{tabular}{@{}lcc@{}}
\toprule
& Before & After \\
\midrule
Seeds per side per layout & 4 & 24 \\
Layouts & 12 & 12 \\
Rollouts per cell & 96 & 576 \\
Interval half-width & $0.117$ & $0.046$ \\
\bottomrule
\end{tabular}
\end{center}

Note the top-right of that table against the margin: at a half-width of $0.117$,
the interval is wider than the entire $\pm 0.10$ band. The old design could not
have certified equivalence at \emph{any} observed value, not even at exactly
$0.5$. That is the quantitative reason a difference test had been standing in for
an equivalence test: the equivalence test would have failed everything.

\section{The check that broke inside the fix}
\label{sec:degenerate}

This is the part I would show a student, because it is the same mistake
reappearing one level down, inside its own repair.

AUROC is a rank statistic --- it only looks at ordering. If every score it is
asked to rank is tied, the standard implementation returns exactly $0.5$, by the
convention that ties count half. Not because the two arms were compared and found
indistinguishable. Because \emph{nothing was compared}.

Now feed that into the new equivalence test. Every layout returns exactly $0.5$,
so the bootstrap standard error is $0$, so the confidence interval collapses to
the single point $[0.5000, 0.5000]$, so it fits inside any margin whatsoever ---
$0.10$, or $0.001$, or anything. The test passes, always, and cannot fail.

That is precisely the defect the equivalence test was introduced to remove. The
first ledger the new gate produced certified 15 of its 35 cells this way. Every
one of them belonged to a family whose proxy reward is \emph{constant by
construction}. A constant score is trivially matched. It is also completely
uninformative, and the gate could not tell those apart.

\subsection{Two guards, and a third verdict}

The gate now asks two questions before it will read an equivalence test at all.

\textbf{Could the statistic have come out differently?} For each layout it
computes what fraction of cross-arm run pairs the detector strictly orders. If
the attainable range of the AUROC already fits inside the equivalence band, the
test was decided before the first rollout.

\textbf{Did the signal mean anything?} The first guard alone is cheap to defeat.
A proxy reward of $0.675 + \mathcal{N}(0, 10^{-7})$ --- a constant plus jitter
eight orders of magnitude below the reward, which no consumer of a reward could
act on --- pushes the ordering fraction to $0.961$ and the whole gate reports
success. No tie tolerance fixes this, because jitter ten times larger than the
tolerance always clears it. So the second guard is a property of the family, not
of the scores: the pooled proxy reward's standard deviation as a fraction of its
own magnitude, with a floor at $10^{-4}$.

Neither guard subsumes the other. On the current grid each catches three families
the other cannot see.

And the verdict is now three-valued:

\begin{center}
\begin{tabular}{@{}lp{9.5cm}@{}}
\toprule
PASS & Measured, and matched within the margin. \\
FAIL & Measured, and outside the margin. The score leaks; every other number on
       that cell is suspect. \\
DEGENERATE & \textbf{Could not be measured at all.} Licenses nothing, in either
       direction. \\
\bottomrule
\end{tabular}
\end{center}

DEGENERATE is not a soft failure and it is emphatically not a pass. Filing that
third case under the first is the mistake this whole audit is about, and it
happened twice at two different levels: before the fix, ``I failed to detect a
leak'' was published as ``there is no leak''; after the fix, ``I could not look''
was published as ``I looked, and it was fine''. Same error. The second one
survived a repair aimed at the first.

\subsection{Where the ledger currently stands}

Of the 50 cells currently in scope: \textbf{15 admitted, 30 degenerate, 5
genuinely failed}. Admitted is a minority of the grid, and the count fell from an
earlier ``30 of 35 admitted'' not because any family got worse, but because the
new guard stopped counting cells whose tests were never actually run.

And the scope itself is limited, which I would rather state than have you find:
the ledger covers \textbf{10 of the 33 families}. The other 23 are uncertified,
which is not the same as certified-and-passing.

\section{What I think the research question is}
\label{sec:point3}

You asked whether my interest is in constructing benchmarks or in experimental
rigour, how I would change the status quo, and --- the sharpest version ---
whether I am sure there is a real problem in the literature.

Let me answer the last one first, because the honest answer is no.

The paper this repository accompanies claims a failure class: checks that cannot
return a negative verdict under the design the benchmark ships. It offers three
diagnostics for finding them. It also includes a pre-registered survey of 19
published benchmarks, run specifically to test whether the class generalises
beyond my own work.

\textbf{It does not.} The survey did not find the pattern elsewhere in the form
found here, and that is reported in the paper as a claim withdrawn. So my
position is: I found this in one benchmark, mine, and when I went looking for it
in nineteen others under a protocol I fixed in advance, I did not find it. What
survives is the method and a detailed case study, not a claim about the field.

A second prediction of mine failed recently and is worth recording for the same
reason. Earlier work of mine concluded that the ``true rewards differ'' check is
blind to hacking that \emph{adds to} a competent agent rather than
\emph{substituting for} competence. I predicted that two categories in an
external corpus would be of the additive kind. They are not --- all of them turn
out to avoid doing the real work. The prediction was wrong and the check is not
obviously blind in the way I claimed.

With that said, here is what I actually want to work on, stated concretely enough
to be attacked:

\begin{quote}
When an evaluation produces a number, is that number evidence about the thing the
evaluation says it measures?
\end{quote}

That splits into two questions I can actually test:

\begin{enumerate}
\item Can you demonstrate, before reporting any score, that a benchmark's entry
      checks are capable of rejecting something? A criterion is not a check until
      it comes with a demonstration that it can fail --- a power curve, or an
      adversarial probe that passes it. A negative control is decorative unless
      the failures are published next to the passes.
\item Does a result that holds in-distribution survive a perturbation stated in
      advance? The $0.994 \to 0.508$ collapse is one instance: the perturbation
      was named first, and the result did not survive it.
\end{enumerate}

You are right that people already evaluate their own tests, more or less
rigorously. My claim is narrower than ``nobody does this'': it is that auditing
your own benchmark is currently a one-off event you write a paper about, rather
than a routine step with a standard form. I do not have a framework for making it
routine. I have one worked example and three diagnostics.

On your point about hyperparameters --- you are right, and it made me drop a word
I had been using loosely. Nothing is robust to arbitrary perturbation, and any
algorithm can be made ill-conditioned on purpose. So ``is this robust?'' has no
answer. ``Does this specific result survive this specific perturbation, named in
advance?'' does.

\section{What this project does not show}

Collected in one place, so you do not have to trust me to volunteer them
individually.

\begin{itemize}
\item \textbf{The cheating is scripted.} 28 of 33 families are hand-written
      policies, as in Section~\ref{sec:pair}. This is about what a channel
      contains in principle, not about real learned agents.
\item \textbf{The public scoreboard is a single draw.} Every cell is one
      unreplicated 5-versus-5 comparison. The standard error near $0.5$ is about
      $0.19$. Do not read its third decimal, and do not rank two detectors that
      differ by less than about $0.2$. This is fixed for the aggregate numbers ---
      those come from the 20-draw replication --- but not for individual cells.
\item \textbf{All 30 detectors share that draw}, so their cell values are
      correlated and their differences are not independent measurements.
\item \textbf{The certified set is not the scored set.} The entry checks average
      over 12 layouts; the scoreboard evaluates one.
\item \textbf{L0 sitting at chance is a negative control, not a discovery.} The
      families are \emph{built} so that reward-only detectors cannot work. An
      earlier version of the README reported this as an empirical finding that
      ``reward-only monitoring fails''. That was wrong. The result is useful only
      in the failure direction: an L0 detector rising above chance means the
      construction leaked.
\item \textbf{One scoreboard row is a duplicate.} The detector labelled ``Perfect
      Feature Oracle'' at L3 is a subclass of an L2 detector that overrides only
      its name and its declared level. It never reads the true reward. It agrees
      with its parent on 33 of 33 families. It is kept as a labelled cross-check
      and excluded from every aggregate, but the old ``L3 mean over $n=2$'' figure
      averaged one oracle with one copy of an L2 baseline and measured nothing.
\item \textbf{The onset half is unvalidated.} The project was published as
      ``Reward Hacking \emph{Onset} Benchmark''. That column of the scoreboard is
      not currently supported. The acronym is kept for URL stability only, and the
      expansion should not be used.
\item \textbf{The entry checks are barely exercised by the test suite.} The
      full-certification path is never invoked on a registered family anywhere in
      the tests --- the two tests that touch it use synthetic fixtures. A green
      test suite here means ``the screens that exist passed'', not ``the families
      are certified''.
\end{itemize}
